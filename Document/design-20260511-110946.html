Design: SPZ 웹 뷰어 v2 — 풀 시스템 진입 전 vertical slice 결정

Generated by /office-hours on 2026-05-11 Branch: main Repo: D:\GitHub\Work\spzFirst (Three.js+Spark 스파이크 통과 상태) Status: APPROVED (2026-05-11, spec review 9/10 통과) Mode: Intrapreneurship Supersedes: design-20260508-164539.html

이 문서가 왜 새로 작성되었나

세션 1 디자인 문서는 "3주 안에 잃은 클라이언트용 단일 영업 URL 데모를 만든다"를 narrowest wedge로 잡았다. 세션 2(2026-05-11)에서 사용자가 두 가지를 새로 결정했다.

  1. 시간 압박 없이 완성도 높게 가져간다. 3주 데드라인은 더 이상 절대 제약이 아니다.
  2. myWorkTodo.md의 12개 요구사항(에디터 모드, 다국어, 씬 이동, JSON 파이프라인, 2D 스프라이트 등)이 1차 데모 안에 포함되어야 한다.

이 두 결정의 합산 효과로, 세션 1 디자인 문서의 Premise 5("3명 팀이 풀 시스템부터 만드는 것은 부적절하다")가 사실상 폐기됐다. 1차 데모 = "단일 영업 URL"이라는 정의도 폐기됐다. 따라서 새 디자인 문서가 필요하다.

추가로 콘텐츠 도구를 Unity에서 Unreal로 변경했다. 세션 1 디자인 문서가 Unity 출신 3명 팀과 Unity 워크플로를 전제했던 것에 영향을 준다.

Problem Statement

회사는 Unity 기반 360도 파노라마 웹 서비스를 운영 중이다. 잃은 10억 카테고리(공간 안에 실제 같은 3D 모델 배치 + 퀄리티 일관성)를 회복해야 한다.

세션 1에서 검증된 사실.

  • SPZ(3D Gaussian Splatting) 포맷이 폴리곤 모델의 퀄리티 일관성 문제를 우회한다는 모델러 가설은 유효하다.
  • Three.js 0.180.0 + @sparkjsdev/spark 조합으로 웹에서 SPZ 렌더링이 동작한다(index.html 스파이크 통과).
  • 자체 1인칭 카메라 컨트롤이 동작한다(WASD + 마우스 룩 + 속도 조절).

세션 2에서 추가된 요구.

  • 풀 시스템으로 가야 한다. 단발성 데모가 아니라 회사 표준 콘텐츠 파이프라인이 되어야 한다.
  • 콘텐츠 작업은 Unreal에서 한다. Unreal에서 SPZ 공간 + 모델 배치를 확인하고 JSON으로 export한 뒤, 웹이 그 JSON을 읽어 동일하게 재현한다.
  • 웹 측은 에디터 모드(이동/회전 + 계층 구조), 1인칭 이동, 3D 모델 + 2D 스프라이트 + 클릭, 다국어, PC/모바일 분기, 씬 이동(start/loading/mainscene00/01 등)을 모두 지원해야 한다.
  • 사용자 본인은 웹 프로그램이 처음이다. 학습 곡선이 작업 일정에 포함되어야 한다.

Demand Evidence

세션 1 디자인 문서의 수요 근거가 유효하다. 단가 10억 원 이상 클라이언트 프로젝트 1건 무산 + 그 카테고리 자진 퇴장. 이번 세션에서 추가로 변경된 정보는 없음. 단, 합격 기준이 다층화되면서 수요 검증도 다층화된다(아래 Success Criteria 참고).

Status Quo

  • 현재 코드 베이스: index.html 단일 파일. Three.js 0.180.0 + @sparkjsdev/spark + esm.sh CDN 임포트맵. 빌드 도구 없음.
  • 통과한 검증: SPZ 적재, X축 180° 좌표계 보정, 1인칭 카메라, 디버그 HUD.
  • 미착수: 모델 배치, IBL 라이팅, JSON 파이프라인, 에디터 모드, 다국어, 씬 시스템, 2D 스프라이트, PC/모바일 분기.

Target User & 새 narrowest wedge

1차 사용자(B2B 사내): 사내 마케팅·기획·쇼룸팀 PM. 이번 세션에서 추가됨: 사내 모델러/콘텐츠 제작자가 Unreal에서 작업하는 사람으로 명시.

최종 수혜자: 외부 클라이언트(브랜드/기업)의 의사결정자.

새 narrowest wedge (세션 1 정의를 대체):

"Unreal에서 SPZ 공간 + GLB 모델 1개를 배치하고, 그 배치 정보(좌표/회전/스케일)를 JSON으로 export한 뒤, 웹이 그 JSON을 읽어 동일한 공간에서 동일한 위치에 모델을 띄운다. Unreal에서 모델을 옮기면 웹이 새로고침 시 같은 위치로 반영된다."

이 한 줄짜리 끝-에서-끝 관통 슬라이스가 작동하면, 이후 풀 시스템의 모든 항목(에디터 모드, 다국어, 씬 이동 등)이 이 vertical slice의 두꺼움을 늘리는 작업으로 정의된다.

의도적으로 빠지는 것 (이 vertical slice에서만): 에디터 모드, 다국어, 다중 씬, 클릭 인터랙션, 모바일 분기, 2D 스프라이트. 첫 번째 slice 통과 후 다음 차례로 정한다.

Constraints

  • 팀: 개발 인력 3명(Unity 출신). Unreal 학습 곡선 새로 추가됨. 사용자 본인은 웹 프로그램이 처음.
  • 환경: 웹 브라우저(데스크탑·모바일). 콘텐츠 도구는 Unreal.
  • 기간: 절대 데드라인 없음. 완성도 우선. 다만 잃은 카테고리의 시장 신호가 살아있는 동안 회수해야 함(PM/영업 측 확인 필요).
  • 빌드 시스템: 현재 단일 HTML. 1500줄 초과 또는 다중 파일 필요 시 Vite 도입 검토(CLAUDE.md 명시).

Premises

새 전제 묶음. 이전 디자인 문서의 Premise 5는 폐기. 다른 전제는 유효.

  1. 모델러는 .spz 포맷으로 출력 가능하다. (세션 1 그대로)
  2. 회사 서비스는 웹 배포가 필수다. (세션 1 그대로)
  3. 3DGS의 Lumen급 양방향 다이나믹 라이팅은 본 프로젝트의 합격 기준이 아니다. IBL 하이브리드로 충분. (세션 1 그대로)
  4. Niantic의 SPZ 포맷 의존성은 합리적이다. (세션 1 그대로)
  5. 3명 팀이 6개월 풀 시스템부터 만드는 것은 부적절하다. 폐기. 시간을 가져가고 완성도 우선.
  6. (신규) 콘텐츠 도구는 Unreal이다. Unity는 사내 기존 도구였으나 신규 작업은 Unreal 기준.
  7. (신규) Unreal에서 SPZ를 안정적으로 다룰 수 있다. 이 전제는 부분 검증됨(2026-05-11 사전 조사). Niantic 공식 Unreal plugin 부재 확인. 대부분 plugin이 PLY 입력. 실용 경로는 "SPZ → PLY 변환 → Luma AI Unreal Plugin(무료) 적재". 변환 도구는 nianticlabs.github.io/spz (브라우저 WASM, 설치 불필요). 실제 렌더링 검증은 액션 1에서. 상세: Document/research-unreal-spz-20260511.html.
  8. (신규) 단일 영업 데모는 풀 시스템의 부분집합으로 자연스럽게 포함된다. 별도 트랙이 아니라 풀 시스템 진행 중에 시연 가능한 상태가 되면 그게 영업 자료가 된다.

Cross-Model Perspective

본 세션은 단축 진행되어 Codex 제3자 리뷰를 거치지 않았다. 다음 office-hours 세션에서 풀 시스템 디자인을 본격 작성할 때 cross-model 검토를 권장한다.

Approaches Considered

다음 1~2주의 첫 번째 vertical slice를 어떻게 그을지에 대한 후보.

Approach A: Unreal → JSON → 웹 한줄 관통 제너레이터 (선택)

  • 개요: Unreal에서 SPZ 공간 + GLB 모델 1개 배치 → JSON export → 웹이 JSON 읽어 동일 재현.
  • 검증되는 것: Unreal SPZ 호환성, JSON 스키마 최소 필드, 웹 측 로더 설계 한꺼번에.
  • 장점: 한 번에 3개 미지수 해소. 두꺼워질 때 다른 모든 항목이 이 슬라이스에 붙는 구조.
  • 단점: Unreal SPZ 호환성 깨지면 일정이 미끄러짐. 첫 슬라이스 자체가 가장 큰 도박.
  • 위험 완화: Unreal SPZ 처리 경로(직접 적재 / 변환 후 적재 / 둘 다 불가)를 1~3일 안에 결정. 불가 시 Approach B로 회전하되, 회전 후에도 더미 JSON은 v0.1 스키마 문서를 따라 작성. Unreal 트랙 복구 시 스키마 마이그레이션 비용을 최소화. 더미와 실제 export 간 스키마 분기는 허용하지 않음.

Approach B: 웹 측 더미 JSON으로 모델 배치 + 클릭 먼저

  • 개요: Unreal 합류는 나중에. 손으로 쓴 더미 JSON으로 index.html이 GLB 모델 배치 + 클릭 이벤트 처리.
  • 장점: 사용자(웹 담당)가 즉시 손댈 수 있음. Unreal 검증 대기로 막히지 않음.
  • 단점: 스키마가 임의대로 정해질 위험. Unreal export 코드를 작성할 때 다시 맞춰야 할 가능성 큼.

Approach C: PlayCanvas + SPZ 호환성 검증 먼저

  • 개요: 세션 1 디자인 문서의 권고 스택을 1주 검증. 가능하면 PlayCanvas 비주얼 에디터 활용.
  • 장점: 사용자가 "웹 처음"이라 비주얼 에디터의 가치가 큼. UI 작업 진입 부담이 크게 줄어듦.
  • 단점: 도구 결정에 1주 더 투자. 안 되면 도구 결정만 끝나고 진척 없음.

Approach D: JSON 스키마 + 폴더 구조부터 문서로 확정

  • 개요: 코드 쓰기 전에 계약서를 종이로 먼저 확정.
  • 장점: Unreal·웹 둘 다 재사용. 재대용성 최고.
  • 단점: 가장 추상적이라 진척 체감이 약함. "웹 처음" 사용자가 학습보다 문서 작성에 시간 쓰게 됨.

Recommended Approach

Approach A: Unreal → JSON → 웹 한줄 관통 제너레이터

단계

1주차: Unreal SPZ 처리 경로 결정 + JSON 스키마 v0.1 + export prototype

  • 0일차 (반나절): 스키마 합의 미니 회의 — Unreal 담당자 + 사용자 30분. 좌표계/단위/회전 표현/경로 표기 등 1쪽 메모 합의. The Assignment 2번 참고.
  • 1~3일차: Unreal SPZ 처리 경로 결정 (모델러 또는 Unreal 담당자 주체).
    • 시도 후보 순서: (1) Niantic 공식 Unreal plugin 존재 확인 → (2) LumaAI Unreal plugin → (3) UE5 Gaussian Splatting 커뮤니티 plugin → (4) SPZ→PLY/KSplat 변환 후 plugin 적재.
    • 합격: Unreal 에디터 뷰포트에서 SPZ(또는 변환 결과)가 정상 렌더링 + 카메라 컨트롤 가능.
    • 어느 경로든 안 되면: 즉시 Approach B로 회전. Unreal SPZ 트랙 별도 분리.
  • 3~5일차: GLB 변환 + JSON export 코드 작성.
    • Unreal 자산(FBX/Datasmith 등)을 GLB로 변환 (Unreal Datasmith Exporter, glTF Exporter plugin 등 사용 검토).
    • Unreal 씬 안에 배치된 모델의 좌표/회전/스케일/모델 식별자를 JSON으로 저장.
  • 1주차 합격 기준: Document/json-schema-v0.1.html 작성 + scene00.json 1개와 scene00.glb 1개가 작업 폴더에 저장.

2주차: 웹 측 JSON 로더 + 모델 배치 코드 (사용자가 주체, "웹 처음" 학습 곡선 포함)

  • 예상 일정: JSON fetch + 파싱 1일 → GLB 로더(GLTFLoader) 1일 → Three.js scene 좌표계 매핑 2일 → Unreal export 결과로 검증 1일. 학습 시간 포함 시 1.5~2주 가능.
  • 합격 기준이 1주에 빡빡하면 두 단계로 분리:
    • 2주차 전반(1주): 정적인 손-편집 JSON으로 모델 1개 화면에 띄우기.
    • 2주차 후반(0.5~1주): Unreal 새 export 결과 반영 검증.
  • 2주차 종합 합격: Unreal에서 옮긴 모델 위치가 웹 새로고침 시 정확히 반영.

검증 후 분기

  • 합격 → 다음 1~2주 차례 결정. 후보: 다중 모델 배치, 클릭 이벤트, JSON 스키마 v0.2 확장. **에디터 모드는 1~2주 분량의 별도 vertical slice로 분리(본 슬라이스에 합치지 않음).**
  • 부분 합격(렌더는 되는데 좌표계 어긋남) → 좌표계 변환 레이어 추가 후 재검증.
  • 실패(Unreal SPZ 안 됨) → Approach B로 회전 + Unreal SPZ 트랙 별도 분리.

풀 시스템 초벌 윤곽

본 문서가 풀 시스템 디자인을 본격 작성하지는 않는다(다음 office-hours 세션 작업). 다만 JSON 스키마 v0.1이 풀 시스템의 기둥(다국어 키, 씬 ID, 모델 type 등)을 동시에 결정하기 때문에 윤곽만 1쪽으로 깔아둔다. 풀 시스템 디자인 작성 시 이 윤곽을 입력값으로 사용.

예상 모듈 구성 (잠정):

  • Scene Manager: 씬 ID로 JSON 로드, 씬 전환(start → loading → mainscene00 → mainscene01), 라이프사이클.
  • Asset Loader: GLB 로드 + 캐시, SPZ 로드(Spark), 2D 스프라이트 텍스처 로드.
  • JSON Schema Loader: 스키마 버전 인식, v0.1/v0.2 변환 레이어 (스키마 진화 대비).
  • Input/Movement: 1인칭 이동, PC/모바일 입력 분기 (현재 1인칭 컨트롤 코드 베이스).
  • Editor Mode (별도 slice): 이동/회전 + 계층 구조 트리 UI.
  • i18n Layer: 다국어 자원 구조. 키 체계는 JSON 스키마 v0.1 결정 시 양립 가능하도록 미리 합의.
  • UI Layer: 클릭 인터랙션, 정보 팝업, PC/모바일 분기 레이아웃.

v0.1 스키마 결정 시 양립 가능성 검토 항목:

  • models[].type: "3d" / "sprite" 구분 가능한 필드 자리 마련.
  • models[].click_action: 클릭 동작 미정이지만 자리 마련.
  • i18n_keys: 모델 이름·설명 등 다국어 키 자리 마련(v0.2에서 실제 사용).

  • 필수 최소 결정 (1주차 시작 전에 굳혀야 함):
    • schema_version 필드 포함.
    • position: 단위 = meter. 좌표 = (x, y, z).
    • rotation: quaternion (x, y, z, w) 권장 (Unreal Pitch/Yaw/Roll degrees → quaternion 변환 후 export). 또는 Euler 사용 시 회전 순서 명시.
    • coord_system: Unreal(left-handed, Z-up) vs Three.js(right-handed, Y-up) 차이 명시. 변환은 웹 측에서.
    • glb_path: JSON 파일 기준 상대 경로.
    • JSON 파일 인코딩: UTF-8 without BOM.
  • 필드 후보: scene_id, schema_version, coord_system, models[] (id, glb_path, position, rotation, scale).
  • 진화 경로: v0.1은 1주차 작성 → 2주차 실제 데이터 통합 검증 → 깨지면 v0.2. 1주차 합격은 "문서 존재", 2주차 합격은 "실제 데이터로 통과".

What I noticed about how you think

본 세션에서 관찰된 신호.

  • 시간을 자기 자원으로 인식했다. "급하게 진행 하지 않아도 되서 천천히 완성도 높게 가지고 가고 싶어"라는 한 줄은 office-hours의 가장 큰 forcing question(3주 데드라인 vs 풀 요구사항) 자체를 우회하는 방식으로 풀었다. 데드라인을 외부 제약으로 받아들이지 않고 본인의 결정으로 옮겨놓은 것. 사내 프로젝트에서 자주 보기 어려운 자세.
  • forcing question 묶음을 한 번 거절했다. 첫 번째 옵션 묶음(잃은 클라이언트 의사결정 영향 분류)에 답하지 않고 "급하지 않다, 완성도 우선"이라는 자기 답을 던졌다. 진단의 선택지가 본인 영역(개발)을 넘어선 곳(영업 의사결정)으로 들어가자 그 답을 받지 않고 자기가 답할 수 있는 영역으로 대화를 끌어왔다. 흐릿한 흐름에 휩쓸리지 않는 것은 세션 1에서도 관찰된 패턴.
  • "차례대로 진행하자"라는 단어 선택. 한꺼번에 모든 결정을 내리지 않고 차례를 두자는 자세. vertical slice 정신과 일치. 웹 작업이 처음인 사람이 자주 보이는 패턴은 "전체 아키텍처를 한꺼번에 그리고 시작"인데, 정반대로 갔다.
  • Unity에서 Unreal로 결정했다. 디자인 문서 v1이 Unity 출신 3명 팀을 가정해서 PlayCanvas를 권고했던 흐름을 한 줄로 바꿨다. 이 결정의 결과(팀 학습 곡선, Unreal SPZ 미검증)는 본 디자인 v2의 가장 큰 미지수 두 개를 만들었지만, 결정 자체는 단호했다.
