## Problem Statement

회사는 Unity 기반 360도 파노라마 웹 서비스를 운영 중이다. 사내 마케팅·기획·쇼룸팀이 외부 클라이언트(브랜드/기업)에게 인터랙티브 3D 콘텐츠를 납품하는 데 사용한다.

문제는 두 층이다.

**1층 (기술 부채)**: Unity → WebGL 빌드 시 폴리곤 3D 모델의 렌더 퀄리티가 파노라마(고해상도 사진) 대비 현저히 낮다. 그래서 "공간 안에 실제 같은 3D 모델 배치" 요구가 들어오면 퀄리티 일관성을 맞출 수 없어 모델 배치를 포기해왔다. 한 번은 단가 10억 원 이상의 클라이언트 프로젝트가 이 한계 때문에 무산되었고, 그 이후 회사는 "실시간 3D 모델 배치"가 포함된 카테고리의 발주를 자진하여 받지 않고 있다.

**2층 (포맷 호환성)**: Niantic이 오픈소스로 공개한 SPZ 포맷(.ply 대비 ~10배 작은 3DGS 압축 포맷)을 도입하면 위 문제를 우회할 수 있다는 모델러의 가설이 있다. Unity 에디터/네이티브 빌드에서는 SPZ가 동작하지만, **Unity WebGL 빌드에서는 SPZ가 동작하지 않는다.** 회사 서비스는 웹 배포가 필수이므로 Unity WebGL은 막다른 길이다.

따라서 결정해야 할 것은 두 가지이다.
- (a) SPZ를 웹에서 안정적으로 렌더링할 수 있는 비-Unity 스택 선택
- (b) 그 스택이 모델러 가설(3DGS 공간 + 인터랙티브 3D 모델 배치 + 퀄리티 일관성)을 실제로 충족하는지 2~3주 데모로 검증

## Demand Evidence

- 단가 **10억 원 이상**의 클라이언트 프로젝트 1건이 "실시간 3D 모델 배치" 요구를 못 맞춰 무산됨.
- 그 이후 회사는 같은 카테고리의 발주를 **자진해서 거절**하고 있음. 즉 시장 수요가 들어오는데 공급 능력 부재로 매출 기회를 시스템적으로 포기 중.
- 위 두 사실의 합산 = 카테고리 자진 퇴장. 1년에 1~2건만 회복해도 ROI는 자동으로 양수.

수요 데이터의 한계: 정확한 연간 거절 건수와 카테고리 시장 사이즈는 본 디자인 문서 작성 시점에 미파악. PM/영업 측 데이터로 별도 보강 필요.

## Status Quo

- 콘텐츠 파이프라인: 모델러가 .spz 파일 생성 → Unity 프로젝트에 적재 → WebGL 빌드 → 웹 배포 → 사내 팀이 외부 클라이언트에게 URL 전달.
- 현재 한계: WebGL 빌드 시 SPZ 미동작, 폴리곤 3D 모델은 동작은 하나 퀄리티 일관성 부족. → 모델 배치 기능을 운영에서 배제 중.
- 우회 수단: 정적 영상 별도 제작, 정적 이미지 대체, 또는 발주 거절.

## Target User & Narrowest Wedge

**1차 사용자 (B2B 사내)**: 사내 마케팅·기획·쇼룸팀 PM. 외부 클라이언트 프로젝트의 사내 책임자. 본 도구는 그들이 클라이언트에게 보여줄 인터랙티브 3D 콘텐츠를 제작·배포하는 파이프라인.

**최종 수혜자**: 외부 클라이언트(브랜드/기업)의 의사결정자. 그들이 콘텐츠 퀄리티를 보고 발주 의사를 굳힌다.

**Narrowest Wedge (가장 작은 검증 단위)**:

> "잃었던 그 10억 프로젝트의 공간 1개 + 들어가야 했던 3D 모델 1~2개를 PlayCanvas + 3DGS(SPZ) + IBL 환경 조명 하이브리드로 재현한 단일 페이지 웹 데모. URL 하나로 영업이 클라이언트에게 보낼 수 있는 형태."

합격 기준 (사전 확정 필수): **잃은 그 클라이언트의 의사결정자(또는 같은 카테고리의 신규 잠재 클라이언트)가 데모를 보고 "다시 진행해도 되겠다"고 말하는가.** 이 한 가지만 본다.

의도적으로 빠지는 것: 콘텐츠 업로드 UI, CMS, 권한 관리, 다중 사용자, 결제, 관리자 대시보드. 풀 시스템 설계는 검증 통과 후로 미룬다.

## Constraints

- 팀: 개발 인력 3명, 모두 Unity 출신, 웹(JS/TS) 전문 개발자 부재.
- 환경: 웹 브라우저 (모바일은 별도 네이티브 앱 없이 웹으로 접속).
- 도구 요구사항: UI 작업이 편해야 함 (비주얼 에디터 기반 워크플로 선호).
- 기술 제약: Unity WebGL은 SPZ 미동작으로 사실상 사용 불가.
- 기간: 1차 데모 2~3주 가설 (검증 결과 후 재계획).

## Premises

다음 전제들에 동의해야 본 디자인이 유효하다. 동의 안 되는 항목이 있으면 디자인을 수정해야 한다.

1. **모델러는 .spz 포맷으로 출력 가능하다.** (기존 Unity 워크플로에서 사용 중이므로 이미 검증됨.)
2. **회사 서비스는 웹 배포가 필수다.** 네이티브 모바일 앱 또는 데스크톱 클라이언트 옵션은 검토 대상 아님.
3. **3DGS의 Lumen-급 양방향 다이나믹 라이팅은 본 프로젝트의 합격 기준이 아니다.** 잃은 클라이언트의 요구는 Level A(공간 안에 실제 같은 모델이 자연스럽게 들어 있어 보이게)였으므로, IBL(image-based lighting) 기반 환경 조명 흉내로 충족 가능.
4. **Niantic의 SPZ 포맷 의존성은 합리적인 선택이다.** 오픈소스 + 활발한 생태계 + 성능적 이점이 락인 리스크보다 크다.
5. **3명 팀이 6개월 풀 시스템부터 만드는 것은 부적절하다.** 1차 산출물은 2~3주 검증 데모이며, 검증 결과에 따라 후속 단계 재설계.

## Approaches Considered

### Approach A: PlayCanvas (선택)
- **개요**: 웹 네이티브 게임 엔진. 비주얼 에디터(Hierarchy/Inspector/Scene/Asset Browser) 보유. Unity와 사용감이 가장 비슷.
- **GS 지원**: 베타 단계로 진행 중. 자체 GS 렌더 통합 또는 커뮤니티 플러그인 활용 가능.
- **SPZ 처리**: 빌드 시 SPZ → PLY/KSplat 변환하거나, WASM 디코더 통합. SPZ 변환 도구는 Niantic 오픈소스에 포함.
- **장점**:
  - Unity 출신 3명 팀의 학습 비용 최소 (1~2주 내 생산성).
  - UI 작업 편의성 최상 (비주얼 에디터, Template 시스템).
  - 게임 식 인터랙션(모델 배치, 충돌, 카메라, 입력) 네이티브 지원.
  - 모바일 웹 호환 (WebGL/WebGPU).
  - 프로덕션 안정성 검증됨 (대형 인터랙티브 광고/제품 시연 사례 다수).
- **단점**:
  - GS 지원이 아직 베타 → 미세한 렌더 이슈 가능, 검증 스파이크 1주 필요.
  - PlayCanvas 호스팅 플랜은 유료 (소규모 프로젝트는 무료 티어, 상업용은 월 단위 구독). 자체 호스팅도 가능 (엔진 MIT 라이선스).
  - SPZ 변환 파이프라인 별도 구축 필요.
- **위험 완화**: 1주 스파이크로 GS 렌더 + SPZ 통합 가능성 검증 후 본 데모 착수.

### Approach B: Three.js + mkkellogg/GaussianSplats3D
- **개요**: 게임 엔진이 아닌 3D 라이브러리 조합. 가장 가볍고 자유도 최고.
- **GS 지원**: 커뮤니티 라이브러리 중 가장 활발. PLY/KSplat 지원, SPZ는 직접 변환.
- **장점**: 번들 작음. 커스터마이징 자유도 최고. JS/TS 인력 풀 두꺼워 채용·외주 쉬움.
- **단점**: **본 팀의 결정적 결격 사유**: 웹 개발자 부재. 게임 식 인터랙션, UI 시스템, 게임 루프, 입력 처리, 충돌 등을 모두 직접 구현해야 함 → 결국 미니 엔진을 만들게 됨. UI 비주얼 에디터 부재.
- **결론**: 본 팀 구성과 UI 편의성 요구를 충족 못 함. 탈락.

### Approach C: Niantic 8th Wall
- **개요**: Niantic 자사 웹 AR/VR 플랫폼. SPZ 1차 지원.
- **장점**: SPZ 호환성 최상. AR 확장 자연스러움. 인프라 호스팅 포함.
- **단점**: 모바일 AR 확장 계획이 없는 본 프로젝트엔 강점이 의미 없음. 월 구독비 + 사내 락인 + 게임 로직 자유도 PlayCanvas보다 낮음.
- **결론**: 비용 대비 가치 낮음. 향후 AR 확장 시 재검토. 탈락.

### Approach D: WebAssembly + 자체 렌더러
- **개요**: SPZ 디코더(C++ → WASM) + 자체 GS 렌더러(WebGPU).
- **장점**: 외부 의존 0, 풀 컨트롤, 차별화 가능.
- **단점**: 개발 기간 3~6개월 R&D + 영구 유지보수 부담. 게임 엔진 미경험 3명 팀에 비현실적.
- **결론**: 사내 도구 ROI에 부적합. 탈락.

## Recommended Approach

**Approach A: PlayCanvas + 3DGS(SPZ) + IBL 하이브리드**

### 단계 (예상 일정)

**Week 1: 기술 검증 스파이크**
- PlayCanvas의 GS 렌더 통합 검증 (베타 기능 안정성 확인).
- SPZ → PlayCanvas 적재 파이프라인 구축 (변환 또는 WASM 디코더).
- 합격 기준: 임의의 .spz 파일이 PlayCanvas 빈 씬에서 안정적으로 렌더링 + 카메라 컨트롤 가능.
- 실패 시: Approach 재검토 (Babylon.js 또는 Three.js+커스텀 UI 풀백).

**Week 2: 1차 데모 구현**
- 잃은 그 10억 프로젝트의 공간 1개 + 모델 1~2개 재현.
- PlayCanvas 비주얼 에디터로 씬 구성, 카메라 경로, 모델 배치 인터랙션 (클릭/드래그).
- 폴리곤 모델은 PBR + IBL 환경 조명 (3DGS 공간에서 환경맵 샘플).
- 게임 식 진행: 정해진 경로 또는 자유 탐색 + 모델 정보 팝업.

**Week 3: 합격 기준 검증**
- 잃은 클라이언트의 의사결정자 또는 동급 신규 잠재 클라이언트 1명에게 시연.
- 피드백 수집: "다시 진행하겠다" / "이 부분만 더" / "여전히 부족".
- 결과에 따라 후속 분기:
  - 합격 → Phase 2 풀 시스템 설계 착수 (CMS, 권한, 다중 사용자 등).
  - 불합격 (퀄리티 부족) → 양방향 라이팅 R&D 경로 검토 또는 프로젝트 보류.
  - 검증 자체 불가 (시연 대상 없음) → PM/영업 측 검증 협업 우선 처리.

## Open Questions

본 디자인 문서를 PM/스폰서와 합의하기 전에 명확화 필요한 항목들.

1. **잃은 그 클라이언트와 재미팅이 가능한가?** 영영 떠났다면 동급 잠재 클라이언트 확보가 데모 검증의 전제 조건.
2. **거절 중인 카테고리의 연간 발주 예상 건수와 합산 단가는 얼마인가?** 사내 ROI 정당화 자료에 필수.
3. **PlayCanvas의 호스팅 비용은 회사 IT 정책에 적합한가?** 사내 호스팅 필수라면 자체 호스팅 옵션 검토.
4. **모델러의 SPZ 출력이 PlayCanvas/3DGS 호환 표준에 맞는가?** Niantic 표준 SPZ인지 확인 필요.
5. **2~3주 동안 3명 팀의 시간을 본 데모에 풀로 배정 가능한가?** 다른 운영 업무와 병행이면 일정 재산정 필요.

## Success Criteria

1. **기술 검증**: PlayCanvas + 3DGS(SPZ) + IBL 하이브리드로 폴리곤 모델 배치 시, 공간과 모델의 시각적 퀄리티 격차가 현재 Unity WebGL 대비 명확히 개선되어 있다.
2. **사용자 검증**: 잃은 클라이언트(또는 동급 잠재 클라이언트) 1명이 시연을 보고 "다시 진행해도 좋다"는 의사를 구두로 표현한다.
3. **팀 운영**: 3명 팀이 PlayCanvas로 1차 데모를 3주 내 출시한다.

## Distribution Plan

본 1차 데모는 사내 도구 배포가 아닌 **단일 영업 자료**이다. 배포 채널은 다음과 같다.

- 정적 호스팅: PlayCanvas 자체 퍼블리시 또는 회사 정적 웹 서버 (S3/CloudFront 등).
- URL 단일: 영업이 클라이언트 미팅 후 메일로 첨부할 수 있는 형태.
- 인증: 1차 데모는 비공개 URL (UUID 기반) 충분. 본격 도구화 시 권한 시스템 별도 설계.

CI/CD: 1차 데모는 수동 배포. 풀 시스템화 시점에 PlayCanvas 빌드 → S3 업로드 자동화.

- 영업/PM으로부터 클라이언트 (또는 동급 잠재 클라이언트) 시연 약속 확보.
- PlayCanvas 계정 및 라이선스 확인.

## What I noticed about how you think

본 office-hours 진행 중 관찰된 신호들. 이후 Phase 2 설계에 도움이 될 맥락.

- **모델러 가설을 본인이 직접 의심했다.** "3DGS 모델이 배경의 Lumen 효과를 받을 수 있나?" 라는 질문은 office-hours 진행자가 묻기 전에 본인이 먼저 던진 것. 셀 포인트가 정말 작동하는지에 대한 기술적 회의력이 살아있다는 것은 본 프로젝트에서 가장 중요한 자산.
- **결정적 정보를 끝에 정정해주었다.** "나는 개발 포지션이라 위의 내용은 모르겠음"이라는 한 줄로 office-hours를 잘못된 영역에서 끌어내 진짜 기술 결정 영역으로 데려왔다. 흐릿한 흐름에 휩쓸리지 않고 자기 영역의 진실을 명확히 던지는 것은 사내 프로젝트에서 드문 자질.
- **"사례 없음"을 솔직히 답했다.** Q1에서 거짓으로 답을 만들지 않고 부재를 인정한 것. 이 한 줄이 진단의 출발점이 되었다. 진실 우선 태도는 향후 PM과의 합의에서도 작동할 것.
