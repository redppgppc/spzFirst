Premises

새 전제 묶음. v2의 Premise 7 폐기는 무효화되고 P1로 부활. P7(충돌 통합)이 신설.

  1. P1 — NanoGS plugin이 "길 A(Unreal에서 SPZ 직접 시각화 + 좌표 추출)"를 안정적으로 가능하게 한다. 근거: 시각 정상 / 설치 / 이동·회전·스케일 / 실시간 fps 5단계 검증 OK. PLY property 순서 자유, INRIA spec 준수, SH bands 자동 감지. 좌표계 자동 변환(COLMAP/OpenCV Y-down → UE Z-up, 100x scale).
  2. P2 — 모델러 회신은 정보 수집용으로만 의미 있다. 길 B(메쉬 프록시) 결정용 의미는 폐기. NanoGS가 받는 PLY spec이 충분히 관대해서 모델러 측 SPZ 도구가 어떤 PLY를 출력하든 호환 가능성 큼.
  3. P3 — 길 B(메쉬 프록시 방식 폐기) fallback 두지 않음. 단순화 우선. NanoGS 실패 시 본 디자인 전체 재검토.
  4. P4 — 디자인 v3는 v2의 길 A 부활·개선 형태. Premise 7 폐기 결정이 NanoGS 발견으로 무효화됨.
  5. P5 — 1주차 vertical slice = Unreal NanoGS PLY 배치 → 좌표 JSON export → 웹 SPZ 동일 위치 표시. v2의 시작점 그대로.
  6. P6 — 좌표계 일치 검증은 별도 단계 두지 않고 1주차 webview 동기화 시점에 자연 검증. 어긋남 발생 시 export 코드에서 보정.
  7. P7 (신규) — 충돌 메쉬 처리는 1주차 슬라이스에 통합한다. 콘텐츠 제작자가 Unreal에서 명시적으로 작업한 collision mesh를 export하는 단일 경로. SPZ 공간 충돌 + 모델 클릭이 myWorkTodo.html 1차 데모 합격 기준에 포함되므로 별도 슬라이스로 미루지 않는다. NanoGS auto collision 경로는 폐기. 웹 측은 invisible GLB mesh로 받아 Three.js raycast/movement에 사용.

v2의 P1–P4, P6, P8 (모델러 SPZ 출력 / 웹 배포 / 3DGS Lumen급 라이팅 / Niantic 의존성 합리 / 단일 영업 데모 자연 포함)은 그대로 유효이므로 v3 본문에 다시 적지 않음.

  • 1주차: Unreal NanoGS PLY 배치 → 좌표·회전·스케일 JSON export. 충돌은 다루지 않음.

Collision 데이터의 위치·형식 (명확화)

중요: PLY 포맷 자체에는 collision이 들어가지 않는다. PLY는 Gaussian Splatting 시각 데이터(point + opacity + scale + rotation + SH coefficients)만 담는 포맷이다.

본 디자인의 collision 처리는 별도 GLB 파일 + JSON에서 묶기 방식이다.

파일 구성

파일 역할 포맷
scene00_space.ply SPZ 공간 시각 NanoGS PLY (Gaussian Splatting)
scene00_collision.glb 1인칭 이동 충돌 + 클릭 raycast 대상 (invisible) 일반 low-poly mesh GLB
model_chair.glb 모델 시각 + 모델 BBox 또는 box collider 일반 mesh GLB
scene00.json 위 3개 파일을 같은 좌표계로 묶는 계약서 JSON

Unreal 측 작업 흐름

  1. NanoGS plugin으로 PLY 적재 → SPZ 공간이 Unreal 뷰포트에 보임.
  2. 그 위에 사용자가 BSP brush 또는 low-poly mesh로 벽·바닥 윤곽 그림 (Unreal에서 작업 시에는 보이지만 웹에서는 invisible로 사용).
  3. 같은 씬에서 모두 export: PLY는 그대로 복사, collision proxy는 GLB로 export, 좌표·회전·스케일은 JSON에 기록.

웹 측 작업 흐름

  1. JSON 읽음.
  2. PLY는 Spark(또는 Niantic SPZ 로더 재변환)에 먹여서 시각으로 띄움.
  3. collision GLB는 Three.js에 적재하되 material.visible = false (또는 디버그 토글로 wireframe).
  4. 1인칭 카메라 이동 시 collision GLB에 raycast → 통과 방지. 모델 클릭은 collision GLB 또는 모델 mesh 대상.

Collision mesh source 결정 (2026-05-13 확정)

결정: 충돌 메쉬는 콘텐츠 제작자가 Unreal에서 명시적으로 작업한 mesh를 export하는 방식으로 한다. NanoGS auto collision 경로는 폐기.

이유:

  • 콘텐츠 제작자가 SPZ 공간 위에 의도적으로 그린 윤곽이 자동 생성보다 정확. 1인칭 이동 시 어디까지 갈 수 있는지가 콘텐츠 결정 사항으로 명확해짐.
  • 풀 시스템 단계에서도 동일 방식으로 일관 가능. 자동 경로와 수동 경로를 혼재시키지 않음.
  • NanoGS auto collision이 가능하더라도 웹용 collision GLB는 어차피 별도 필요(Three.js Gaussian Splat 렌더는 raycast 대상이 아님). 자동 경로는 Unreal 뷰포트 작업 편의만 줄 뿐 export 단계는 동일.

도구 후보 (1주차 0일차 결정):

  • Unreal BSP brush: 가장 단순. 박스·계단·실린더 조합으로 벽·바닥 그림. 작업 빠름. polygon count 자동 관리.
  • Unreal Modeling Mode (UE 5.x 기본 내장): BSP보다 자유로운 mesh 편집. Box·Plane·Extrude·CSG 가능.
  • 외부 DCC(Blender/Maya)에서 low-poly mesh 작성 후 GLB import: 모델러가 익숙한 도구 활용 가능. 단 좌표계 변환 추가 단계.

권장: Unreal Modeling Mode. BSP보다 자유롭고, 외부 DCC보다 좌표계 변환 단계 없음. 사용자/모델러가 직접 NanoGS PLY 시각을 보면서 그 위에 mesh 그릴 수 있음.

Open Questions

  1. collision 작업 도구 + GLB export 도구는 무엇인가? 1주차 1일차 0.5일 결정. 권장: Unreal Modeling Mode + glTF Exporter plugin. (NanoGS auto collision은 P7 확정으로 폐기 — 콘텐츠 제작자가 명시 작업.)

  3. 모델러 측 SPZ 출력 도구가 NanoGS 호환 PLY를 직접 출력하는가, 아니면 SPZ → PLY 변환을 거쳐야 하는가? Document/modeler-consult-20260512.html 1쪽 축소 후 회신 대기.
  4. NanoGS PLY를 웹에서 적재하는 단순한 경로: PLY → SPZ 재변환 후 Spark에 먹임 (가장 단순) vs 웹 측 PLY 직접 파싱. 2주차 1일차 결정.
