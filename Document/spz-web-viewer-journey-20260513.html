SPZ 웹 뷰어 만들기 — 4개 세션의 의사결정 일지

3D Gaussian Splatting(이하 SPZ)을 활용한 웹 뷰어를 0부터 만든 4개의 office-hours 세션 기록. 변환 도구·plugin·좌표계 진단·실패한 시도까지 시간 순으로 정리.

2026-05-08 ~ 2026-05-13

누구를 위한 글인가

  • 3D 콘텐츠 웹 파이프라인을 처음 구축하는 개발자. 어떤 도구를 어떤 순서로 검증해야 하는지 막막한 상태에서 출발하는 사람.
  • Unreal·Unity에서 콘텐츠 만들고 웹에서 보여주려는 모델러·기획자. 좌표계·단위·포맷 변환의 함정이 어디에 있는지 알고 싶은 사람.
  • 3D Gaussian Splatting을 처음 시도하는 사람. SPZ가 무엇인지, INRIA PLY와 어떻게 다른지, 변환 도구가 무엇인지 한 번에 알고 싶은 사람.

이 글은 "정답을 알고 쓴 매뉴얼"이 아니라, 실패와 우회를 거친 후 굳어진 결정의 기록이다. 그래서 도구 이름 외에도 왜 그 도구를 골랐는가 가 함께 적혀있다.

들어가기 전 — 한 줄 요약

모델러 (Postshot) → INRIA PLY
                      │
                      ├─→ Unreal (NanoGS plugin) ─→ 시각 + collision proxy GLB export
                      │                              ↓
                      └─→ splat-transform           좌표·메타데이터 JSON export
                            -H N --spz-version 3    ↓
                            → SPZ v3 (gzip)         ↓
                            → Spark (Three.js) ←────┘
                            (rotation.y = -π/2 보정)

이 chain에 도달하기까지 7가지 PLY 변형 실패, 2개 plugin 폐기, SPZ 포맷 2개 버전(1.x / 2.0) 진단, 좌표계 4개 chain 정렬을 거쳤다.

챕터 1. 시작점 — 왜 SPZ인가

배경

회사는 Unity 기반 360도 파노라마 웹 서비스를 운영 중. 큰 카테고리 1건의 발주가 무산됐고 그 카테고리에서 자진 퇴장한 상황. 재진입의 차별화 요소가 필요했다.

모델러의 가설: 3D Gaussian Splatting(SPZ)이 폴리곤 모델의 퀄리티 일관성 문제를 우회한다. 폴리곤은 카메라 각도·조명에 따라 결과 편차가 크지만, GS는 캡처한 시점의 시각을 그대로 유지한다.

이 가설이 맞는지 가장 빨리 확인하는 방법은? 답: 웹 브라우저에서 SPZ가 정말 렌더링되는지 한 시간 안에 검증한다.

SPZ가 뭔가

  • 3D Gaussian Splatting: 각 점이 3D 가우시안 분포(중심점 + 공분산 + 색상 + 투명도 + 구면조화 SH)인 점군. NeRF의 후속 기법.
  • SPZ (Niantic Gaussian Splat Package): Niantic이 제안한 GS 압축 포맷. gzip 압축된 binary. PLY 대비 ~10배 작음.
  • INRIA PLY: 원조 Gaussian Splatting 논문의 출력 포맷. property 자유, gzip 안 함, 크기 큼.

첫 스파이크 (반나절)

스택 결정:

항목 선택 왜
3D 라이브러리 Three.js 0.180.0 가장 흔하고 검증된 WebGL 라이브러리
SPZ 로더 @sparkjsdev/spark SPZ 네이티브 지원하는 거의 유일한 npm 라이브러리
빌드 도구 없음 (esm.sh CDN) 첫 스파이크는 단일 HTML이 가장 빠르다
카메라 자체 1인칭 yaw/pitch OrbitControls는 타겟 점 주위 공전. 우리는 "자기 위치에서 회전" 필요

{
  "imports": {
    "three": "https://esm.sh/three@0.180.0",

  }

</script>

const spark = new SparkRenderer({ renderer });

test.spz (78MB)를 esm.sh CDN 임포트맵으로 로딩, X축 180° 회전 보정, 1인칭 카메라. 통과. 가설 검증 끝.

학습 포인트

  • 시각 검증을 가장 빨리. 풀 시스템 설계를 그리기 전에 "정말 동작하는가"를 한 시간 안에 본다.
  • ?deps=three@0.180.0 같은 esm.sh 쿼리로 Three.js 인스턴스 중복을 피했다. 같은 라이브러리가 두 번 로드되면 instanceof 체크가 깨진다.
  • e.code (물리 키 코드) 사용. e.key는 한글 IME 영향 받는다. 키보드 이벤트 작성 시 무조건 e.code.

챕터 2. 콘텐츠 도구 — Unity에서 Unreal로

두 가지 큰 결정

세션 2 시작 시점에 사용자(웹 측 개발자)가 두 가지 결정을 들고 왔다.

결정 1: 시간 압박 폐기

이전 세션은 "3주 안에 외부 클라이언트 데모를 만든다"는 narrowest wedge였다. 사용자는 "급하지 않게 완성도 우선"으로 옮겼다. 3주 데드라인이 외부 제약이 아니라 자기 결정으로 옮겨졌다.

이게 왜 큰가? office-hours의 가장 큰 forcing question(데드라인 vs 완성도)을 우회하는 방식으로 풀었다. 사내 프로젝트에서 자주 보기 어려운 자세.

결정 2: 콘텐츠 도구 Unity → Unreal

이전 사전 조사에서 PlayCanvas 권고가 있었지만, 모델러·콘텐츠 팀이 Unreal로 가기로 정했다. 이 한 줄이 디자인 문서 v1을 통째로 무력화시켰다.

사전 조사로 막힐 미래 미리 발견

Unreal에서 SPZ를 어떻게 다룰지 미리 조사:

  • Niantic 공식 Unreal SDK 부재 확인. (Niantic은 Unity SDK만 제공.)
  • 모든 후보 plugin이 PLY 입력 중심. SPZ 직접 적재 plugin은 없음.
  • 실용 경로: SPZ → PLY 변환 → PLY 입력 plugin 적재.

이 사전 조사가 챕터 3의 실패를 줄여주었다 (완전히 막지는 못했지만).

디자인 v2의 narrowest wedge

"Unreal에서 SPZ 공간 + GLB 모델 1개를 배치, 그 배치 정보를 JSON으로 export, 웹이 그 JSON을 읽어 동일 위치에 모델을 띄운다."

한 슬라이스에서 3개 미지수(Unreal SPZ 호환성, JSON 스키마 최소 필드, 웹 측 로더 설계)를 동시에 해소.

학습 포인트

  • 시간 결정을 자기 자원으로 가져오기. 데드라인이 외부에서 주어진 것이 아니라 본인이 정한 것이라 보면 의사결정 폭이 달라진다.
  • 사전 조사는 검색 30분이지만 막힐 미래 며칠을 절약. Niantic Unreal SDK 부재를 디자인 단계에서 알았다.
  • vertical slice의 의미: 한 슬라이스가 통과하면 그 뒤의 모든 작업은 슬라이스의 두꺼움을 늘리는 형태로 정의된다.

챕터 3. 길 A 폐기 + 길 B 채택 + 다시 길 A 부활

이 챕터는 office-hours 두 세션(3, 4)에 걸친 우회의 기록.

길 A 시도 (세션 3)

목표: Unreal에서 SPZ 자체를 시각화. 그 위에 모델 배치, 좌표 export.

시도 1: Luma AI Unreal Plugin

PLY를 import 받았으나 splat이 정상 외형으로 안 나오고 알록달록 줄무늬 + 검정 화면.

원인 가설: PlayCanvas 생태계(SPZ + splat-transform + SuperSplat)가 모두 SPZ-친화 메모리 레이아웃으로 PLY를 출력. Luma는 INRIA 표준 기대.

시도 2: XV3dGS plugin (XVERSE)

PLY 파일 자체를 ply properties header format invalid로 거부. plugin source closed.

시도 3-7: 7종 PLY 변형 모두 거부

  • test.ply (nianticlabs spz JS 변환): 거부
  • test_inria.ply (splat-transform 변환): 거부
  • test_savedas.ply (SuperSplat Save As): 거부
  • test.compressed.ply (SuperSplat 압축): 거부
  • test_inria_ordered.ply (수동 INRIA 순서 재정렬, 자작 Python 도구): 거부
  • test_xv3dgs.ply (INRIA + normal + RGB uchar 추가, plugin binary strings로 spec 추출): 거부

tools/ply_for_xv3dgs.py를 작성하면서 plugin binary의 GSImporter.dll 안의 PLY parser 기대 spec까지 추출했지만, plugin docs Google Docs 권한 차단 + 샘플 PLY 없음으로 외부 spec 역공학 한계 도달.

결정: 길 A 폐기 + 길 B(메쉬 프록시) 채택

신 워크플로: Unreal에서는 SPZ 안 본다. 저폴리 메쉬 프록시로 위치 잡고 좌표 export, 실제 SPZ 렌더링은 웹에서만.

길 A 부활 (세션 4)

사용자가 발견: NanoGS plugin (github TimChen1383/NanoGaussianSplatting).

  • MIT 라이선스, source 전체 공개.
  • UE 5.6, 5.7 지원.
  • 사용자가 5단계 검증 통과: 시각 정상 + 설치 + 이동 + 회전 + 스케일 + 실시간 fps.

source 분석(PLYFileReader.cpp) 결과 결정적 차이:

항목 Luma / XV3dGS NanoGS
PLY property 순서 엄격 자유 (이름 기반 조회)
INRIA spec 부분 완전 준수
SH bands 고정 자동 감지 (1/2/3 bands)
normal/RGB uchar 요구 불요
좌표계 자동 변환 없음 COLMAP/Y-down → UE Z-up + 100x scale
Source closed open, MIT

PlayCanvas 변형 PLY도 그대로 받는다. 7종 PLY 변형 실패의 원인이었던 property 순서 제약이 NanoGS에선 무관.

학습 포인트

  • Closed-source plugin spec 역공학은 한계 있음. binary strings 추출까지 가지만 sample PLY 없으면 검증 불가.
  • Open source plugin의 가치. NanoGS는 MIT + source 공개라 spec 외에 좌표계 변환·SH 처리까지 코드로 확인 가능.
  • fallback을 두지 않는 결정. 길 B(메쉬 프록시) 폐기 후 NanoGS 단독 채택. 실패 시 본 디자인 전체 재검토라는 비용을 짊어진다는 의미. 단순화 우선.
  • 3개월 안에 같은 도구가 다시 나타날 수 있다. closed-source plugin이 막히면 영구 폐기보다 "현재 spec 명세 없어서 폐기, spec 공개 시 재시도"로 기록 남겨둔다.

챕터 4. 표준 변환 chain 구축

NanoGS plugin이 들어오면서 Unreal 측 검증은 통과. 다음 미지수: 웹 측에 SPZ 어떻게 적재하는가.

모델러 도구 정체 확인

모델러가 보내준 SPZ 파일(Matic01.spz)을 웹에서 적재하려는데 첫 시도부터 에러:

Worker error: Invalid gzip header

매직 byte 비교:

test.spz:    1f 8b 08 00 ...     ← gzip magic (Niantic SPZ 1.x)
Matic01.spz: 4e 47 53 50 04 ...  ← "NGSP\x04" (Niantic SPZ 2.0 = NGSP)

SPZ 1.x vs SPZ 2.0:

  • SPZ 1.x: gzip 압축. Niantic 초기 포맷. @sparkjsdev/spark가 받음.
  • SPZ 2.0 (NGSP): Niantic 2024~2025 발표 새 포맷. 비압축, 다른 구조. Spark는 못 받음.

모델러 도구가 NGSP를 출력하고 있다는 의미. 변환 chain이 필요.

다행히 모델러가 같은 capture session으로 PLY도 만들어줬다 (Matic01.ply, 958.9MB). PLY 헤더 분석:

generator: Postshot v1.0.110
vertices:  4,260,709 (4.26M)
properties: x,y,z | f_dc_0..2 | f_rest_0..44 | opacity | scale_0..2 | rot_0..3
total: 59 properties (표준 INRIA full SH bands 3개)

Postshot 확인. 데스크탑 GS training 앱(Windows). INRIA 표준 PLY 직접 출력. NanoGS가 받는 spec과 100% 일치.

splat-transform 발견

PlayCanvas의 splat-transform (npm CLI). 멀티포맷 변환 도구:

SUPPORTED INPUTS:
  .ply  .compressed.ply  .sog  .spz  meta.json  .ksplat  .splat  .mjs  .lcc

SUPPORTED OUTPUTS:
  .ply  .compressed.ply  .sog  .spz  meta.json  lod-meta.json  .glb  .csv  .html

SPZ OUTPUT:
  --spz-version <3|4>  Default: 4

--spz-version 3이 핵심. SPZ 1.x = version 3, SPZ 2.0 = version 4. 양방향 변환 가능.

변환 시도 + 실패 + SH 다운그레이드

npx splat-transform Matic01.ply Matic01_v3.spz --spz-version 3 -w

결과: WASM RuntimeError: Aborted(). 4.26M gaussians + SH 3 bands 출력에서 splat-transform WASM이 abort.

해결: SH bands를 줄임.

npx splat-transform Matic01.ply -H 1 Matic01_v3.spz --spz-version 3 -w
# → SH 3 bands → 1 band 다운그레이드. 958MB → 81.8MB. 성공.

-H 0도 가능 (71MB, 색만, view-dependent 효과 0). 풀 시스템에서 SH 3 full quality가 필요하면 NGSP 지원 라이브러리 검토 (별도 트랙).

변환 chain 1차 확정

모델러 Postshot → INRIA PLY (958MB, SH 3)
                    │
                    ├─→ NanoGS plugin (Unreal): 그대로 import
                    │
                    └─→ splat-transform -H 1 --spz-version 3
                          → SPZ v3 (gzip, 82MB, SH 1)
                          → Spark
                          → Three.js

학습 포인트

  • 포맷 진단은 매직 byte로. 1f 8b = gzip, NGSP = SPZ 2.0, ply\n = PLY ASCII. 첫 8 byte로 90% 진단.
  • 버전 차이를 모르고 라이브러리를 의심하지 말기. test.spz는 잘 되는데 Matic01.spz는 안 됨 → "라이브러리가 큰 파일을 못 받나?" 가설은 틀린 방향. 매직 byte로 격리.
  • WASM 도구 한계 인지. splat-transform이 SH 3 + 4M gaussian + SPZ v3 조합에서 silent abort. -H 1 또는 -H 0으로 회피.
  • 다운그레이드의 시각 영향. SH 3 → 1: 반짝이는 표면(금속·유리·물)에서 view-dependent specular 감소. 무광택 실내라면 거의 차이 없음. 1차 데모엔 SH 1로 충분.

챕터 5. 좌표계 정렬 — 4개 변환 chain의 누락 회전

가장 까다로운 단계. 시각으로만 발견되는 종류의 문제.

좌표계가 만나는 4개 지점

Postshot 출력 PLY     ── COLMAP/OpenCV: Y-down, right-handed
       ↓
splat-transform       ── 변환 규칙 불명 (source 비공개 부분 존재)
       ↓
SPZ v3 (Spark 입력)   ── Niantic SPZ: Y-down 가정 (X축 180° 회전 관례)
       ↓
Three.js (웹 렌더)    ── glTF 표준: Y-up, right-handed

평행 trunk:
Unreal NanoGS plugin ── PLY 적재 시 COLMAP → UE 자동 변환 (Z-up, left-handed) + 100x scale
       ↓
Unreal glTF Exporter ── UE → glTF 자동 변환 (Y-up, right-handed) + 자동 cm → m
       ↓
collision GLB

5개 좌표계 변환이 chain. 어디 하나라도 가정이 다르면 어긋난다.

1차 보정: X축 180° → 0° (옵션 A)

처음 Matic01_v3.spz를 적재하니 위아래 뒤집힘. test.spz는 X축 180° 회전이 기본이었는데, Matic01_v3.spz는 회전 없음이 정상.

왜? Niantic 원본 SPZ(test.spz)는 Y-down 저장 관례 → X축 180°로 Three.js Y-up에 맞춤. Postshot → splat-transform chain은 Three.js Y-up으로 이미 정렬된 채로 출력. 그래서 추가 회전 불요.

splat.rotation.x = 0;          // 기본: 회전 없음
// F 키 토글: Niantic 원본 SPZ 적재 시 X축 180° 회전 (디버그용)

2차 보정: Yaw -90° 추가

Unreal에서 SPZ + 박스를 같은 레벨에 두고 박스를 의도된 위치에 배치, GLB export. 웹에서 SPZ + collision GLB를 같이 적재. 결과: 박스가 SPZ에 비해 yaw 축 시계방향 90° 회전된 위치.

시각 진단을 위해 G 키 cycle 토글 추가:

// G: SPZ Y축 회전 cycle (0 → +90 → 180 → -90 → 0)
const yawSteps = [0, Math.PI / 2, Math.PI, -Math.PI / 2];
let yawIdx = 0;
window.addEventListener('keydown', (e) => {
  if (e.code === 'KeyG') {
    yawIdx = (yawIdx + 1) % yawSteps.length;
    splat.rotation.y = yawSteps[yawIdx];
  }
});

4 케이스 시각 비교. -90° (시계방향 90°) 가 정렬 통과.

최종 보정

splat.rotation.x = 0;            // X축: Postshot chain 기본 0
splat.rotation.y = -Math.PI / 2; // Y축: yaw -90° 보정

학습 포인트

  • 좌표계 변환은 시각으로 가장 빨리 진단. 4개 chain의 변환 규칙을 수학적으로 정확히 파악하기보다, 가능한 90°/180° 회전 조합을 cycle 토글로 시각 비교가 빠르다.
  • 풀 시스템 정식 해결은 JSON 메타데이터. 한 SPZ 파일에 대한 보정 값을 코드에 박지 말고 데이터(JSON 스키마 v0.1의 space.rotation_y_deg: -90)에 둔다. 모델러 도구가 바뀌면 메타데이터만 갱신.
  • 단위·X·Y는 우연히 일치. Unreal glTF Exporter의 cm → m 자동 변환과 Postshot → splat-transform chain의 m 단위 보존이 같은 단위로 만났다. 운이 좋은 케이스. 다른 도구 조합에서는 단위 mismatch도 필요한 보정에 추가.
  • collision proxy를 별도 GLB로 두기 잘했다. SPZ는 raycast 대상이 아니라 (Three.js Gaussian Splat 렌더는 mesh가 아님), collision GLB를 따로 export·적재해서 raycast/movement에 사용.

챕터 6. 충돌 처리 — Three.js는 자동 collision이 없다

Unreal에서 액터에 collision 옵션을 켜면 엔진이 자동으로 처리한다. Three.js는 그렇게 안 된다.

도구 본질 collision 처리
Unreal 게임 엔진 PhysX/Chaos 내장. 자동 처리.
Three.js 렌더링 라이브러리 0 내장. 직접 구현 또는 별도 physics 라이브러리.

옵션 3가지

옵션 1: Raycaster 수동 충돌 (선택)

const ray = new THREE.Raycaster(camera.position, moveDir);
const hits = ray.intersectObject(collisionMesh, true);
if (hits.length > 0 && hits[0].distance < 50) {
  // 50cm 이내에 벽 있음. 이동 막기
}

0 dependency, 한 줄 수준 코드. 1인칭 이동 + 클릭 raycast에 충분.

옵션 2: Physics 엔진 (cannon-es, rapier3d, ammo.js)

캐릭터 컨트롤러, 중력, rigid body 자동. bundle ~수백 KB. 1차 데모엔 과잉. 풀 시스템에 점프·중력 필요할 때 검토.

옵션 3: three-mesh-bvh 가속 raycast

1과 2의 중간. 대용량 mesh에서도 빠른 raycast.

Unreal collision 옵션 살리기

Unreal에서 액터별 collision 옵션을 JSON 메타데이터로 export → 웹이 그걸 읽어 자동 등록:

{
  "models": [
    {
      "id": "chair_01",
      "glb_path": "model_chair.glb",
      "collision_enabled": true,
      "collision_type": "bbox"
    },
    {
      "id": "decoration_01",
      "glb_path": "deco.glb",
      "collision_enabled": false
    }
  ]
}

웹 코드는 JSON 순회 시 collision_enabled: true인 객체만 collision 시스템에 등록. 자동은 아니지만 "Unreal에서 켠 옵션을 1:1로 따라옴" 까지는 가능. 새 모델 추가 시 콘텐츠 제작자가 Unreal에서 옵션만 만지면 웹 코드 손 안 댐.

학습 포인트

  • 렌더링 라이브러리와 게임 엔진의 본질 차이. Three.js는 "그리는 일"만, Unreal은 "그리고 + 시뮬레이션 + 입력 + 사운드". 게임 엔진에서 자동인 것이 라이브러리에서는 직접 구현.
  • 1차 데모와 풀 시스템의 합격선 분리. raycaster로 1차 데모 합격선 충분, physics 엔진은 풀 시스템 단계에서 트리거.
  • 메타데이터를 통한 자동화 흉내. 진짜 자동(엔진 통합)은 아니지만, "옵션 켜고 export → 웹에서 자동 등록"으로 사용자 인식상 자동에 가깝게.

실패 비용 관리

세션 3에서 PLY 7종 변형을 모두 시도한 것은 시간 손실로 보일 수 있다. 하지만 그 시도가 남긴 것:

  • PLY property 자유도가 필요한 도구 vs 엄격 spec 도구의 차이 학습.
  • plugin binary strings로 PLY spec 부분 역공학 경험.
  • 우회 도구(tools/ply_for_xv3dgs.py) 자산 보존 (NanoGS plugin 안정성 깨지면 fallback 카드).
  • 길 B(메쉬 프록시) 채택 결정의 정당화.

NanoGS 발견 후로는 7종 PLY 시도가 무의미해졌지만, 그 시도가 없었으면 NanoGS 발견 후에도 "왜 이게 받는지" 정확히 진단 못 했을 것. plugin source의 "이름 기반 조회"가 결정적 차이라는 것을 알아내기까지의 비교 기준이 7종 실패였다.

학습 포인트

  • 작은 단계로 쪼개기. 30분~1시간 단위로 검증 결과가 나오면 막힘이 명확해진다.
  • 실패도 자산. 사라진 것은 시간이지만 남은 것은 "왜 안 됐는가의 비교 기준". 다음 도구 평가 속도가 빨라진다.
  • office-hours 같은 메타 세션의 가치. 코드 작업과 결정 사이를 분리. 결정이 굳어지면 코드는 빨라진다.

import struct, json

with open('file.glb', 'rb') as f:
    data = f.read()
magic, ver, total = struct.unpack('<4sII', data[:12])
chunk_len, _ = struct.unpack('<I4s', data[12:20])
gltf = json.loads(data[20:20+chunk_len])
print('generator:', gltf['asset'].get('generator'))
for n in gltf.get('nodes', []):
    print('node:', n.get('name'), n.get('translation'), n.get('scale'))

import * as THREE from 'three';
import { SparkRenderer, SplatMesh } from '@sparkjsdev/spark';
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';

const spark = new SparkRenderer({ renderer });
scene.add(spark);

const gltfLoader = new GLTFLoader();
gltfLoader.load('samples/scene00_collision.glb', (gltf) => {
  gltf.scene.traverse(obj => {
    if (obj.isMesh) {
      obj.material.transparent = true;
      obj.material.opacity = 0.0;  // invisible (디버그용은 0.4)
    }
  });
  scene.add(gltf.scene);
});

Three.js Raycaster 수동 충돌 (1인칭)

const ray = new THREE.Raycaster();
function tryMove(camera, moveDir, collisionMesh) {
  ray.set(camera.position, moveDir.clone().normalize());
  const hits = ray.intersectObject(collisionMesh, true);
  const STOP_DISTANCE = 0.5;  // m. 50cm 이내는 막기
  if (hits.length > 0 && hits[0].distance < STOP_DISTANCE) {
    return false;
  }
  camera.position.add(moveDir);
  return true;
}

FAQ

Q. 왜 PlayCanvas를 안 썼나? A. PlayCanvas의 GS 베타가 SPZ 직접 지원이 아직 약하다. Three.js + Spark가 SPZ 네이티브라 검증 속도가 빨랐다. 풀 시스템 단계에 PlayCanvas 재검증 여지는 열어둠.

Q. 왜 Vite/빌드 도구 안 썼나? A. 스파이크 단계는 단일 HTML이 가장 빠르다. esm.sh CDN으로 import map만 쓰면 빌드 단계 0. 1500줄 초과하면 Vite 도입 검토.

Q. 왜 physics 엔진 안 썼나? A. 1차 데모 합격 기준에 점프·중력·rigid body가 없다. 1인칭 이동 + 클릭만 필요. Raycaster 수동 충돌이 충분 + 0 dependency.

Q. SPZ 2.0 (NGSP)을 직접 받는 웹 라이브러리는 없나? A. 2026-05 시점 확인 안 함. Spark의 latest 버전 changelog 확인 필요. 받게 되면 SH 3 full quality 보존 가능 + SH 다운그레이드 불요.

Q. 모델러 도구가 Postshot이 아닌 다른 것이면? A. 변환 chain의 좌표계 yaw 보정 값(space.rotation_y_deg)이 도구별로 다를 수 있다. JSON 메타데이터로 도구별 보정 값을 저장하면 코드 변경 없이 도구 교체 가능.

Q. 다른 SPZ 적재 라이브러리 후보는? A. 2026-05 시점에 자세히 비교 안 함. Spark가 유일하게 native SPZ 지원이라 첫 검증에 채택. 풀 시스템 단계에 SH 3 / NGSP 요구사항 생기면 라이브러리 재평가.

닫는 글

4개 세션 동안의 흐름을 적었지만, 진짜 학습은 "이 도구를 쓰면 된다"가 아니라 "어떻게 진단하고 어떻게 격리할까" 였다.

  • 매직 byte로 포맷 진단
  • plugin source 공개 여부가 도구 선택의 큰 기준
  • 시각 검증을 가장 빠른 진단 도구로 사용
  • 작은 단계로 쪼개기, 각 단계 30분~1시간
  • 실패한 시도도 자산으로 보존

기술 스택은 1년 안에 바뀐다. NanoGS도 splat-transform도 다른 도구로 갈릴 수 있다. 하지만 변환 chain을 메타데이터로 분리 + 시각 검증 우선 + 작은 단계로 쪼개기 같은 메타 패턴은 그대로 남는다.

이 글이 비슷한 길을 가는 다음 빌더의 시간을 며칠 줄여주기 바라며.
